# Sejuk Sejuk Operations — System Overview

## Purpose

This is an assessment-grade internal operations system for a fictional Malaysian air-conditioner service business. It supports the end-to-end workflow:

```text
Admin order
→ technician assignment
→ field service
→ service completion + evidence
→ WhatsApp feedback preparation
→ Manager review / close
→ KPI and controlled operations insight
```

It is intentionally **not** presented as a production identity or automated-messaging system. The public demo uses fictional seeded data and selectable mock roles.

## Role design

| Role | Primary responsibility | Server-enforced assessment boundary |
| --- | --- | --- |
| Admin | Create an order, quote it, assign a technician | Admin route and order-create API require the Admin mock session |
| Technician | See simulated current-user assignments, start work, complete service | Technician route and completion/start APIs require Technician role; assigned technician ID is checked server-side |
| Manager | Review/close completed work, inspect KPIs, query Operations AI | Manager route, transition API and AI API require Manager role |

The role selector is permitted by the brief, but is honestly labelled as a **mock assessment sign-in**. Production needs verified Auth identity, user-to-technician mapping, and identity-bound RLS.

## Workflow and data design

```text
New → Assigned → In Progress → Job Done → Reviewed → Closed
```

The workflow is enforced in domain code and by a PostgreSQL trigger. Key actions write immutable audit events.

Core records:

```text
branches
technicians
service_orders
service_completions
job_attachments
payment_records
manager_reviews
reschedule_events
audit_events
```

Important integrity choices:

- Quote, extra charge, final amount and payment use integer cents; Ringgit is formatted only at the presentation boundary.
- Final amount is a generated database value: `quoted_amount_cents + extra_charges_cents`.
- Order numbers are generated by a database sequence/trigger.
- Job evidence is private Supabase Storage, with at most six evidence files per completion.
- Evidence uploads accept image/video/PDF types and are limited to 20 MB per file by server validation.
- The browser never receives the Supabase service-role key.

## Features implemented

### Admin

- Required customer, service, quote and assignment form.
- Auto-generated `SSS-YYYY-#####` order number.
- Required technician assignment for the standard handoff.
- Newest-created-first order register.
- Audit events for creation and assignment.

### Technician

- Mobile-first assigned-work view with a mock current-field-user selector for Ali, John, Bala and Yusoff.
- Only the selected/assigned technician can start or complete that job on the server.
- Work-done notes, extra charges, remarks, optional payment, final amount calculation and timestamp.
- Up to six job-evidence files.
- Prepared WhatsApp customer-feedback link after completion.

### Manager

- Review queue for `Job Done` and `Reviewed` work.
- Review then close lifecycle controls.
- Weekly completed-job, completed-value and reschedule KPIs.
- Technician leaderboard.
- **Workflow Supervisor:** rule-backed Manager review signals for a material price variance or missing job-evidence files. These signals never change status, accuse staff, or contact anyone.

### Notifications

- A `wa.me` link prepares a completion-feedback message using the order number, technician and completion time.
- It is not WhatsApp Business API delivery. A human reviews and sends it in WhatsApp.

## How AI is integrated

### Boundary

The AI feature is an intentionally bounded **Operations Query Window**, not general chat and not natural-language SQL.

```text
Manager question
→ Manager-only POST /api/manager/ai
→ capability allow-list
→ strict Zod schema validation
→ fixed server-side Supabase read
→ small typed safe result
→ deterministic formatter or verified DeepSeek formatting
→ Manager response card
```

The model has no database client, SQL access, file access, write tool, customer phone, customer address, attachment data, credential, or arbitrary-browsing tool.

### Capability catalogue

| Capability | Named tool | Safe result |
| --- | --- | --- |
| Technician completion lookup | `get_completed_jobs(technician, period)` | Order number, service type, completion time, final amount |
| Leaderboard | `get_top_technician(period)` | Technician name and completed-job count |
| Daily completion count | `count_completed_jobs({ date: "today" })` | Count only |
| Completion KPI | `get_completion_summary(period)` | Completed-job count and total final amount |
| Operational Insight | `get_technician_workload({ period: "this_week" })` | Per-technician aggregate active/completed counts, transparent average and threshold |
| Workflow Supervisor watchlist | `get_workflow_review_watchlist({})` | Order number plus server-derived review flags only |

Tool arguments are Zod-validated with strict objects and fixed enums. Unknown tools, extra arguments and unsupported/private-detail question paths are rejected.

### When DeepSeek is used

DeepSeek is configured server-side through `DEEPSEEK_API_KEY` only.

- Recognised money, workload and Supervisor-watchlist questions route **deterministically** to server logic and are formatted deterministically. They do not need a model request.
- Other supported question patterns use DeepSeek to select **one** named read-only tool.
- If a model formats a tool result, it must return the exact same structured data alongside its answer. If validation fails, the server discards the model wording and uses a deterministic formatter.
- Model requests use a 15-second timeout and temperature `0`.

### Operational Insight heuristic

```text
active technicians
+ current-week Assigned / In Progress counts
→ active-team average
→ max(2 active jobs, ceil(1.5 × average)) threshold
→ Manager-review workload watchlist
```

This is a workload signal, not automatic reassignment or scheduling.

### Workflow Supervisor rules

A completed/reviewed job is flagged only when the underlying facts match a documented rule:

```text
High price variance
= final exceeds quote by at least RM100 and at least 50%

Missing job evidence
= completed/reviewed job has zero job-evidence attachments
```

The Supervisor is derived from the current Manager read model after evidence persistence. It is not a cron-driven model action. A future production system could add an idempotent scheduled reconciliation job, but that is not needed for the assessment.

## Current limitations / production migration path

- Mock cookies are not real authentication or identity binding.
- WhatsApp is a prepared deep link, not automatic delivery or delivery tracking.
- Evidence uploads are route-based; a production system would add signed direct uploads, signature/content inspection, malware scanning, thumbnails and retention controls.
- The Advanced Document Understanding challenge is intentionally not included.
- Production AI should add rate limits, PII minimisation/redaction before external provider calls, monitoring, provider-error alerting and a narrower application database role/RPC boundary.
